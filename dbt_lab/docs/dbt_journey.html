Step 0

The big picture: you already know this

This is how every dbt project works. Data moves left to right, and each box is a table:

Raw tableLoaded by another tool. Messy.
→
Cleaned tableTrim, rename, fix types.
→
Business tablesJoins and business rules.
→
Facts & dimensionsWhat reports and dashboards use.

Each teal box is one SQL file that you write. Everything else we learn builds on this flow.

Takeawaydbt builds this chain of tables, one SQL file per table.
Step 1

Why dbt exists

Picture building that chain with plain SQL scripts, compared with building it in dbt:

Plain SQL without dbt

create table clean_cell_sites as
select site_id,
       trim(site_name) as site_name
from raw.cell_sites;

create table dim_cell_site as
select site_id, site_name
from clean_cell_sites;
  • You must remember to run script 1 before script 2, across 200 scripts.
  • You add drop table if exists everywhere.
  • Nobody notices bad data until a dashboard is wrong.
  • Testing a change overwrites the real table.

dbt with dbt

-- clean_cell_sites.sql
select site_id,
       trim(site_name) as site_name
from raw.cell_sites

-- dim_cell_site.sql
select site_id, site_name
from {{ ref('clean_cell_sites') }}
  • You write only the SELECT, one per file.
  • dbt adds the create table ... as for you.
  • dbt sees the ref() and builds the clean table first.
  • You run everything with one command: dbt run.

Here is what happens when you type dbt run:

You writeA plain SELECT in a .sql file
→
dbt wraps itAdds create table … as and works out the order
→
WarehouseThe table now exists and people can query it
TakeawayYou write SELECT statements. dbt turns them into tables and runs them in the right order.
Step 2

source() first, then ref()

source()

Points at a raw table that dbt did not make. You use it once, in the first cleaning step.

ref()

Points at a table that dbt made from one of your files. You use it for every step after that.

raw.cell_sitesLoaded by another tool
uses source('telecom', 'cell_sites')
stg_telecom__cell_sites.sqlYour cleaning step
uses ref('stg_telecom__cell_sites')
dim_cell_site.sqlYour dimension
-- stg_telecom__cell_sites.sql   (first step → source)
select site_id, trim(site_name) as site_name, upper(technology) as technology
from {{ source('telecom', 'cell_sites') }}

-- dim_cell_site.sql             (later step → ref)
select site_id, site_name, technology
from {{ ref('stg_telecom__cell_sites') }}

In source('telecom', 'cell_sites'), telecom is a group name we chose for our raw tables and cell_sites is the table's name. We register them once in a small YAML file. We'll open that file together later.

TakeawayRaw data: source(). Anything dbt built: ref().
Step 3

The file name becomes the table name

Because we saved the file as stg_telecom__cell_sites.sql, it became the name of the view/table, and we can reference it using the same name?
Yes, exactly. There is no separate place where you name the table. The file name is the name.
You save the filestg_telecom__cell_sites.sql
dbt calls the modelstg_telecom__cell_sites (the file name without .sql)
Created in the databasemain_staging.stg_telecom__cell_sites
Other files use it as{{ ref('stg_telecom__cell_sites') }}

You only ever type the name. dbt adds the main_staging. part in front for you. Where that comes from is a topic for a later step.

One rule follows from this: every file name must be unique in the project, because each name can belong to only one table.

TakeawayFile name = model name = table name. ref() uses that same name.
Step 4

Run it and look at the result

In order, this step built only the cleaning step, stg_telecom__cell_sites. The command below also built the dimension, which skipped ahead; Step 6 builds the dimension properly.

dbt has no window of its own. You type commands in a terminal (Terminal on Mac, PowerShell on Windows, or the terminal panel in VS Code), from inside the dbt_lab folder.

One-time setup

# 1. get the project and go into the dbt folder
cd telecom_aws
git fetch origin claude/youthful-thompson-wi7w7p
git checkout claude/youthful-thompson-wi7w7p
cd dbt_lab

# 2. install dbt in its own Python environment
python3 -m venv .venv
source .venv/bin/activate        # Windows: .venv\Scripts\activate
pip install -r requirements.txt

# 3. load the raw data (plays the loading tool)
python scripts/load_raw.py --day 1

The dbt command

dbt run --select stg_telecom__cell_sites dim_cell_site

dbt run builds models. --select names which ones, using the file names without .sql.

What dbt printed

1 of 2 OK created sql view model  main_staging.stg_telecom__cell_sites
2 of 2 OK created sql table model main_marts.dim_cell_site
Completed successfully
raw.cell_sitesAlready there
→

→

dbt built them in the right order on its own. It read the ref() inside dim_cell_site.sql and knew the cleaning step had to come first.

The SQL dbt actually ran

Your file had only the select. Everything in amber below was added by dbt. Find it in target/run/:

create view "telecom"."main_staging"."stg_telecom__cell_sites__dbt_tmp" as (
    select
    site_id,
    trim(site_name)       as site_name,
    trim(city)            as city,
    upper(technology)     as technology,
    latitude,
    longitude
from "telecom"."raw"."cell_sites"      -- was {{ source('telecom', 'cell_sites') }}
);

The __dbt_tmp ending is dbt building under a temporary name and renaming it at the end, so the real table is never half-built.

Look at the result

python scripts/query.py "select * from main_marts.dim_cell_site"

You get the 4 cell sites, cleaned. The extra cell_site_sk column is an ID column; we'll cover it later.

Takeawaydbt run turned two SELECT files into one view and one table, in the right order, and target/run/ shows the exact SQL it ran.
Step 5

View or table? The folder decides

The answer is in dbt_project.yml. Every file inside a folder gets that folder's setting:

models:
  telecom_dbt:
    staging:                   # every file in models/staging/ ...
      +materialized: view      # ... becomes a VIEW
    marts:                     # every file in models/marts/ ...
      +materialized: table     # ... becomes a TABLE
models/staging/telecom/stg_telecom__cell_sites.sql→ view
models/marts/core/dim_cell_site.sql→ table

dbt calls this setting the materialization: the one word that decides whether dbt writes create view or create table around your SELECT.

View

A saved query. No data is stored. Each time someone reads it, the SELECT runs again on the raw table.

create view main_staging.stg_telecom__cell_sites
as ( select ... )
  • Good for the cleaning step: light work that only other dbt models read.
  • No second copy of the data.

Table

The SELECT runs once during dbt run, and the results are stored. Reading it later is fast.

create table main_marts.dim_cell_site
as ( select ... )
  • Good for dimensions and facts: dashboards query them all day.
  • Fast to read, because the work is already done.
TakeawayThe folder sets the default: staging = view, marts = table. The setting is called the materialization and lives in dbt_project.yml.
