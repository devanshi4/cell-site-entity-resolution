Part 1

The ideas

Three things to understand before writing any dbt.

Step 1

The big picture

This is how every dbt project works. Data moves left to right, and each box is a table:

Raw tableLoaded by another tool. Messy.
→
Cleaned tableTrim, rename, fix types.
→
Business tablesJoins and business rules.
→
Facts & dimensionsWhat reports and dashboards use.

Each teal box is one SQL file you write. dbt never loads the raw data; another tool (Fivetran, Glue, Airbyte) puts it in the warehouse first. dbt only does the steps after that.

Takeawaydbt builds this chain of tables, one SQL file per table.
Step 2

How a warehouse is organised

A warehouse (Snowflake, BigQuery, Redshift, or DuckDB in this project) stores tables in nested containers, like folders on a computer:

DatabaseThe top level. Like a drive.
→
SchemaA folder inside the database.
→
TableA file inside the folder.
→
ColumnsWhat is inside the table.

So a full table name has three parts, database.schema.table. This is what our warehouse holds once the pipeline is built:

telecom                          ← database
├── raw                          ← schema: raw data, loaded by another tool
│   ├── cell_sites               ← table
│   ├── customers
│   └── call_events
├── main_staging                 ← schema: dbt puts cleaning models here
│   └── stg_telecom__cell_sites
└── main_marts                   ← schema: dbt puts dimensions and facts here
    └── dim_cell_site

In Snowflake the same idea might look like database RAW, schema SALESFORCE, table ACCOUNTS. There are no fixed "types" of schema; the names are whatever your company created.

Watch out: "schema" has two meanings. Sometimes people use it for a table's column structure (site_id varchar, latitude double). In dbt configuration, schema always means the folder. The column structure is stored in the warehouse with the table itself; you never type it into dbt.

TakeawayDatabase → schema (folder) → table → columns. A full name is database.schema.table.
Step 3

Why dbt exists

Picture building the chain from Step 1 with plain SQL scripts, compared with building it in dbt:

Plain SQL without dbt

create table clean_cell_sites as
select site_id,
       trim(site_name) as site_name
from raw.cell_sites;

create table dim_cell_site as
select site_id, site_name
from clean_cell_sites;
  • You must remember to run script 1 before script 2, across 200 scripts.
  • You add drop table if exists everywhere.
  • Nobody notices bad data until a dashboard is wrong.
  • Testing a change overwrites the real table.

dbt with dbt

-- clean_cell_sites.sql
select site_id,
       trim(site_name) as site_name
from {{ source('telecom', 'cell_sites') }}

-- dim_cell_site.sql
select site_id, site_name
from {{ ref('clean_cell_sites') }}
  • You write only the SELECT, one per file.
  • dbt adds the create table ... as for you.
  • dbt reads ref() and builds the clean table first.
  • One command runs everything: dbt run.

The {{ ... }} parts are Jinja, a templating language. Before anything reaches the warehouse, dbt replaces each one with a real table name. Part 2 shows exactly how.

TakeawayYou write SELECT statements. dbt turns them into tables and runs them in the right order.
Part 2

Build the cell sites pipeline

In the same order you would in a real project: connect, point to the raw table, clean it, run it, then build a dimension on top.

Step 4

Connect dbt to the warehouse

Before dbt can build anything, it needs to know which warehouse to connect to and which database to use. That lives in a file called profiles.yml. A second file, dbt_project.yml, says which connection the project uses.

dbt_project.yml

name: telecom_dbt
profile: telecom_dbt   # use this connection

Lives in the project, in git. Describes the project.

profiles.yml

telecom_dbt:
  target: dev
  outputs:
    dev:
      type: duckdb
      path: telecom.duckdb   # the database
      schema: main

Holds the connection details. In a company it lives on your laptop (~/.dbt/), not in git, because it contains passwords.

In this project the warehouse is a DuckDB file, and DuckDB names the database after the file: telecom.duckdb gives a database called telecom. That is where the word telecom at the front of every table name comes from.

On Snowflake you write the database name directly:

telecom_dbt:
  target: dev
  outputs:
    dev:
      type: snowflake
      account: ab12345
      user: devanshi
      password: "{{ env_var('SNOWFLAKE_PASSWORD') }}"   # never typed into the file
      warehouse: TRANSFORMING
      database: ANALYTICS           # the database dbt connects to and builds in
      schema: dbt_devanshi
Takeawayprofiles.yml is where the database is defined. Every table name dbt writes starts with it unless you say otherwise.
Step 5

Point dbt to the raw table

The raw table raw.cell_sites was loaded by another tool, so dbt does not know about it yet. You register it once in a small YAML file, called a sources file, next to your cleaning model:

models/staging/telecom/
├── _telecom__sources.yml        ← the sources file
└── stg_telecom__cell_sites.sql  ← the cleaning model (Step 6)

These are the lines that matter. The real file has a few more (descriptions and checks), covered later.

version: 2

sources:
  - name: telecom          # source name: a label YOU choose for this group of raw tables
    schema: raw            # the schema (folder) the tables are in
    tables:
      - name: cell_sites   # the table's real name

In a model you then write {{ source('telecom', 'cell_sites') }}. This is a call to the source() function. Its two arguments are the source name and the table name from this file.

Where each part of the real table name comes from

You write{{ source('telecom', 'cell_sites') }}
dbt writes"telecom"."raw"."cell_sites"
database telecomFrom profiles.yml (Step 4). Not from the source name.
schema rawFrom schema: raw in the sources file.
table cell_sitesFrom - name: cell_sites in the sources file.

The source name telecom and the database telecom are two different things that happen to use the same word here. The source name is only a label you use inside dbt; it never appears in the SQL dbt writes.

If the raw data lives in a different database from the one in profiles.yml (common in Snowflake), add one line:

sources:
  - name: telecom
    database: RAW            # overrides the database from profiles.yml
    schema: raw
    tables:
      - name: cell_sites

Now the same {{ source('telecom', 'cell_sites') }} becomes RAW.raw.cell_sites. Your SQL file does not change.

dbt checks the names for you

Correct name works

dbt compile --inline \
 "select * from {{ source('telecom', 'cell_sites') }}"

select * from "telecom"."raw"."cell_sites"

Typo error

dbt compile --inline \
 "select * from {{ source('telecom', 'cell_site') }}"

depends on a source named
'telecom.cell_site' which was not found

The typo is caught before anything touches the warehouse. And if the loading team moves the raw tables to another schema, you change one line here instead of every SQL file.

TakeawayThe sources file registers raw tables. source('telecom', 'cell_sites') takes the schema and table from it, and the database from profiles.yml (or from a database: line).
Step 6

Write the cleaning model

In dbt, each SQL file is called a model. The first, cleaning layer is called staging, so this is a staging model. It is one SELECT, nothing else:

-- models/staging/telecom/stg_telecom__cell_sites.sql
select
    site_id,
    trim(site_name)       as site_name,
    trim(city)            as city,
    upper(technology)     as technology,
    latitude,
    longitude
from {{ source('telecom', 'cell_sites') }}

Your SELECT chooses the columns, as in normal SQL. source() only says where the table is.

The file name becomes the table name

There is no separate place where you name the table:

You save the filestg_telecom__cell_sites.sql
dbt calls the modelstg_telecom__cell_sites (the file name without .sql)
Created in the warehousemain_staging.stg_telecom__cell_sites
Other models use it as{{ ref('stg_telecom__cell_sites') }}

dbt adds the schema (main_staging.) in front for you; where it comes from is a later topic. Because each name belongs to exactly one table, every file name must be unique in the project. The naming style stg_<source>__<table> (with a double underscore) is a common convention, not a rule.

TakeawayA model is one SELECT in one file. File name = model name = table name.
Step 7

Run it

dbt has no window of its own. You type commands in a terminal (Terminal on Mac, PowerShell on Windows, or the terminal panel in VS Code), from inside the dbt_lab folder, the one that contains dbt_project.yml.

One-time setup

# 1. get the project and go into the dbt folder
cd telecom_aws
git fetch origin claude/youthful-thompson-wi7w7p
git checkout claude/youthful-thompson-wi7w7p
cd dbt_lab

# 2. install dbt in its own Python environment
python3 -m venv .venv
source .venv/bin/activate        # Windows: .venv\Scripts\activate
pip install -r requirements.txt

# 3. load the raw data (this script plays the loading tool)
python scripts/load_raw.py --day 1

Build the cleaning model

dbt run --select stg_telecom__cell_sites

1 of 1 START sql view model main_staging.stg_telecom__cell_sites ... [RUN]
1 of 1 OK created sql view model main_staging.stg_telecom__cell_sites [OK]
Done. PASS=1

dbt run builds models. --select names which ones, using the model name (file name without .sql). Without --select, dbt builds every model in the project.

The SQL dbt actually ran

Your file had only the SELECT. Everything in amber was added by dbt. You can find it in the target/run/ folder:

create view "telecom"."main_staging"."stg_telecom__cell_sites__dbt_tmp" as (
    select
    site_id,
    trim(site_name)       as site_name,
    trim(city)            as city,
    upper(technology)     as technology,
    latitude,
    longitude
from "telecom"."raw"."cell_sites"      -- was {{ source('telecom', 'cell_sites') }}
);

dbt builds under a temporary name ending in __dbt_tmp, then renames it at the end, so the real one is never half-built. There is also a target/compiled/ folder, which holds just your SELECT with the Jinja replaced; that is handy for pasting into a SQL editor.

The warehouse now

raw.cell_sitesTable · raw data, loaded by another tool
source()
main_staging.stg_telecom__cell_sitesView · your cleaning model (new)
Takeawaydbt run --select builds one model. dbt wraps your SELECT, swaps source() for the real name, and target/run/ shows exactly what it ran.
Step 8

View or table? The folder decides

The log said view. That choice is called the materialization: the word that decides whether dbt writes create view or create table around your SELECT. Its default is set per folder in dbt_project.yml:

models:
  telecom_dbt:
    staging:                   # every model in models/staging/ ...
      +materialized: view      # ... becomes a VIEW
    marts:                     # every model in models/marts/ ...
      +materialized: table     # ... becomes a TABLE

View

A saved query. No data is stored. Each time someone reads it, the SELECT runs again on the raw table.

  • Good for staging: light work that only other models read.
  • No second copy of the data.

Table

The SELECT runs once during dbt run and the results are stored. Reading it later is fast.

  • Good for dimensions and facts: dashboards query them all day.
  • Fast to read, because the work is already done.
TakeawayThe materialization decides view or table. The folder sets the default: staging = view, marts = table.
Step 9

Build the dimension

A dimension is a table that describes things (here: cell sites) and that reports filter and group by. It reads from your staging model, never from the raw table. It sits in models/marts/, so it becomes a table.

-- models/marts/core/dim_cell_site.sql
select
    {{ surrogate_key(['site_id']) }} as cell_site_sk,   -- a unique ID per site
    site_id,
    site_name,
    city,
    technology,
    latitude,
    longitude
from {{ ref('stg_telecom__cell_sites') }}              -- reads YOUR staging model

The ref() function points to another model by its name. dbt replaces it with the real name and learns that this model must run after the staging model. The first line uses a small helper (surrogate_key) to give each site its own ID; helpers come later.

source()

For raw tables dbt did not build. Registered in a sources file. Used in staging models.

ref()

For models dbt built. Needs no registration; the file is enough. Used everywhere after staging.

Run it

dbt run --select dim_cell_site

1 of 1 OK created sql table model main_marts.dim_cell_site
Done. PASS=1

dbt turned the ref() into the staging model's real name:

from "telecom"."main_staging"."stg_telecom__cell_sites"    -- was {{ ref('stg_telecom__cell_sites') }}

Look at the result

python scripts/query.py "select site_id, site_name, city, technology from main_marts.dim_cell_site"

S01  Bandra West Macro   Mumbai  5G
S02  Andheri East Small  Mumbai  4G
S03  Hinjewadi Phase 1   Pune    4G
S04  Connaught Place     Delhi   5G

The finished cell sites pipeline

raw.cell_sitesTable · raw data, loaded by another tool
source('telecom', 'cell_sites')
main_staging.stg_telecom__cell_sitesView · staging model
ref('stg_telecom__cell_sites')
main_marts.dim_cell_siteTable · dimension
TakeawayRaw data: source(). Anything dbt built: ref(). ref() also tells dbt the order to build things in.
Step 10

Make dbt check the data (tests)

A test is a check dbt runs on a model after it is built. Each test is a SELECT that looks for bad rows:

0 rows found pass

Nothing bad in the data.

1+ rows found fail

The query found bad rows. The number tells you how many.

Where you write tests

In a YAML file next to the model, called a properties file (here models/staging/telecom/_telecom__models.yml):

models:
  - name: stg_telecom__cell_sites        # which model (its file name)
    columns:
      - name: site_id                    # which column
        data_tests: [unique, not_null]   # which checks

In plain words: in stg_telecom__cell_sites, every site_id must be unique and must not be empty. unique and not_null are built-in tests: you only name them, and dbt writes the SQL. The file also checks that technology is 4G or 5G (a built-in test called accepted_values).

What dbt turns each test into

not_null

-- rows with an empty site_id
select site_id
from main_staging.stg_telecom__cell_sites
where site_id is null

unique

-- site_ids that appear twice or more
select site_id, count(*)
from main_staging.stg_telecom__cell_sites
where site_id is not null
group by site_id
having count(*) > 1

These are the queries you would write yourself to check for empty IDs and duplicates. You can see them in target/compiled/.

Run the tests

dbt test --select stg_telecom__cell_sites --indirect-selection cautious

PASS not_null_stg_telecom__cell_sites_site_id
PASS unique_stg_telecom__cell_sites_site_id
PASS accepted_values_stg_telecom__cell_sites_technology__4G__5G
Done. PASS=3

The extra --indirect-selection cautious is needed for now because the properties file also has a test linking cell sites to call records, which are not built yet. It means: only run tests that belong fully to what I selected. After Step 11 you can drop it.

What a failure looks like

We added two bad rows to raw.cell_sites: a duplicate S01 and a site with no ID. The same command then gave:

FAIL 1 not_null_stg_telecom__cell_sites_site_id
FAIL 1 unique_stg_telecom__cell_sites_site_id
PASS   accepted_values_stg_telecom__cell_sites_technology__4G__5G

FAIL 1 means the test query found one bad row. There was no need to run dbt run again: the staging model is a view (Step 8), so it reads the raw table live.

dbt build: stop bad data from spreading

dbt build builds each model, tests it, and only then moves on. With the bad rows still in raw:

dbt build --select stg_telecom__cell_sites dim_cell_site --indirect-selection cautious

OK     created view  stg_telecom__cell_sites
FAIL 1 unique_stg_telecom__cell_sites_site_id
FAIL 1 not_null_stg_telecom__cell_sites_site_id
SKIP   relation main_marts.dim_cell_site      ← not built
raw.cell_sitesHas bad rows
→
stg_telecom__cell_sitesBuilt
→
TestsFAIL
→
dim_cell_siteSkipped. Keeps its last good version.

The bad rows never reached the dimension, and dashboards kept reading the last good version. Once the raw data was clean again, the same command built everything and all 7 checks passed (3 on the staging model, plus 2 the dimension has in its own properties file in models/marts/core/).

dbt runBuilds models only.
dbt testRuns tests only.
dbt buildBuilds each model, tests it, and skips everything downstream if a test fails. What companies run in production.
TakeawayA test is a SELECT that looks for bad rows; zero rows means pass. You add tests in YAML by name, and dbt build stops bad data from reaching the next table.
Reference

Words to know

The official names for things, and what people often call them by mistake.

Warehouse
The system that stores and queries the data: Snowflake, BigQuery, Redshift, DuckDB.
Database
The top level inside the warehouse. Set in profiles.yml.
Schema
A folder inside a database that holds tables, e.g. raw, main_staging.In dbt config it never means the column list.
dbt project
The folder with dbt_project.yml and all your models.
Model
One .sql file with one SELECT. dbt builds it into a view or table.Not "a dbt table" or "a script".
Staging model
The first, cleaning model for one raw table: trim, rename, cast.Not "the source table". In dbt, "source" means the raw table.
Source
A raw table that dbt did not build, registered in a sources file.
Sources file
The YAML file with a sources: block (here _telecom__sources.yml).
Source name
The label you choose for a group of raw tables (- name: telecom).Not the database name, even when it is the same word.
source() function
{{ source('telecom', 'cell_sites') }}. Points to a raw table. Often called "a source reference".
ref() function
{{ ref('stg_telecom__cell_sites') }}. Points to another model. Often called "a ref".
Jinja
The templating language inside {{ }}. dbt replaces it with real SQL before running.
Compile
dbt replacing the Jinja to produce plain SQL. Saved in target/compiled/.
Materialization
Whether a model becomes a view or a table (and later: incremental).
Dimension
A table describing things (sites, customers) that reports filter and group by.
profiles.yml
Connection details: warehouse type, database, schema, credentials.
dbt_project.yml
Project settings: name, which profile to use, folder defaults.
Test (data test)
A check on a model: a SELECT that looks for bad rows. 0 rows = pass.
Built-in test
A test dbt already knows: unique, not_null, accepted_values, relationships.
Properties file
A YAML file with a models: block that adds tests and descriptions to models (here _telecom__models.yml).
dbt build
Builds and tests models in order; skips downstream models when a test fails.
Downstream
Models that read from a given model (dim_cell_site is downstream of stg_telecom__cell_sites). Upstream is the opposite.
Config key
A setting in a YAML file, like schema: raw.Not a variable.
