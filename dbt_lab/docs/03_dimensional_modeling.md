# Section 3 — Facts, dimensions, materializations, macros

## 3.1 Star schema in one picture

```
                       dim_date (date_day)
                              │
dim_customer (customer_sk) ── fct_calls (event_id) ── dim_cell_site (site_id)
     SCD2: 1 row/version      │  1 row per event      Type 1: current only
                              │
                       dim_plan (plan_code)  ← from a seed
```

- **Fact** = an *event* or *measurement*, usually with numbers you sum: `duration_sec`, `data_mb`, `usage_charge`.
  It has many rows, keeps growing, and is narrow.
- **Dimension** = the *context* you filter and group by: who, where, what plan, when.
  It has fewer rows, is wide and descriptive.

## 3.2 Grain is the first decision, always

> **Grain = what one row represents.** Write it at the top of every fact.

`fct_calls`: *one row per `event_id`*. It's enforced by the `unique` test on `event_id`.

Get the grain wrong and every downstream `SUM` is wrong. Example: if `fct_calls` joined
`dim_customer` on `customer_id` only (no time condition), C002 has 3 versions, so each of her
calls would appear **3 times** and her revenue would triple. The `unique` test on `event_id` is what
catches it. **This is the single most common star-schema bug, and AI writes it all the time.**

Other grains you could choose, each a separate model:
- `fct_daily_customer_usage`: one row per customer per day (aggregated, faster for BI)
- `fct_billing_cycles`: one row per customer per month (what Finance invoices)

## 3.3 Dimension types used here

| Model | Type | Why |
|-------|------|-----|
| `dim_customer` | **SCD Type 2** (history) | Plan and city change, and revenue must use the plan *at call time* (Section 5) |
| `dim_cell_site` | **Type 1** (overwrite) | If a site gets renamed, reports should just show the new name |
| `dim_plan` | Type 1, from a **seed** | Small lookup owned by the pricing team |
| `dim_date` | **Generated** | Nobody loads a calendar; we build it with `range()` and `var()` |

Choosing Type 1 vs Type 2 per attribute is a **business** question: *"If a customer moves city,
should last month's calls show the old city or the new one?"* Network planning wants the old city
(where the traffic actually was). Marketing might want the current one. In this project
`fct_calls.customer_city_at_event` stores the city at event time, and `dim_customer` with
`is_current` gives you today's city.

## 3.4 Surrogate keys

`dim_customer.customer_sk = md5(customer_id || valid_from)`. It's generated by our macro
`macros/surrogate_key.sql` (a hand-written copy of `dbt_utils.generate_surrogate_key`).

Why not just use `customer_id`? In an SCD2 dimension `customer_id` **repeats** (one row per version),
so it can't be the primary key. The surrogate key identifies one *version*, and the fact stores it.

## 3.5 Materializations: how a SELECT becomes an object

| Materialization | dbt runs | Use for | In this repo |
|-----------------|----------|---------|--------------|
| `view` | `create view as select` | Staging. Cheap, always fresh, no storage | all `stg_*` |
| `table` | `create table as select` (full rebuild every run) | Dims, small/medium marts | `dim_*`, `rpt_*` |
| `incremental` | First run: create table. After that: insert/merge only new rows | Big, append-heavy facts | `fct_calls` (Section 4) |
| `ephemeral` | Nothing. Inlined as a CTE into whatever refs it | Small reusable logic you don't want as an object | (none) |
| `materialized_view` | Warehouse-managed MV | Platform-specific | (none) |
| *snapshot* | Not a materialization, a separate resource type | SCD2 | `snap_customers` |

The decision is a **cost/latency trade-off** that only you can judge. A view over 5 billion CDRs
that every dashboard hits gets recomputed on every page load. A table rebuilt every hour over
5 billion rows burns warehouse credits. That's why big facts are incremental.

## 3.6 Macros and Jinja (just enough)

A macro is a function that **returns SQL text**. Open `macros/billable_minutes.sql`:

```sql
{% macro billable_minutes(duration_col) -%}
    cast(ceil({{ duration_col }} / 60.0) as integer)
{%- endmacro %}
```

In `fct_calls.sql`, `{{ billable_minutes('duration_sec') }}` becomes
`cast(ceil(duration_sec / 60.0) as integer)`. Check it in `target/compiled/`. The billing rule
lives in **one** place.

Jinja you will see in every repo:

| Syntax | Meaning |
|--------|---------|
| `{{ expr }}` | Print a value into the SQL (`ref`, `source`, `var`, macros, `this`) |
| `{% if / for / set %}` | Control flow; prints nothing itself |
| `{# comment #}` | Jinja comment, removed at compile time |
| `{{ var('date_spine_start') }}` | Variable from `dbt_project.yml` or `--vars` |
| `{{ target.name }}` | `dev` / `prod`, e.g. to limit data in dev: `{% if target.name == 'dev' %} where event_date > current_date - 3 {% endif %}` |

**Gotcha we hit while building this lab:** a `-- SQL comment` *inside* `{{ config(...) }}`
is a Jinja syntax error, because Jinja doesn't know SQL comments. Use `{# #}` there.

Don't over-macro. If a reviewer has to open five macros to understand one model, that's worse
than repeating a `case` statement twice.

## 3.7 Read the fact

Open `models/marts/core/fct_calls.sql` and find:
1. the grain comment at the top
2. `ref()` to staging and to the dimensions (never `source()`)
3. the **point-in-time join** to `dim_customer` (explained in Section 5)
4. pricing: billable minutes × the rate of the plan *valid at the time*
5. `rpt_daily_usage_by_city.sql`, the dashboard-shaped aggregate built *on top of* the fact

```bash
python scripts/query.py "select event_id, customer_id, plan_code, billable_minutes, usage_charge from main_marts.fct_calls order by 1"
```

## What AI can / cannot do here

| AI does well | AI gets wrong | Your call as the DE |
|---|---|---|
| Drafting a star schema from a list of tables | **Joins an SCD2 dim on the natural key only**, which multiplies fact rows | **The grain** of every fact. Everything else follows from it |
| Writing `dim_date`, surrogate key macros | Puts measures in dimensions or descriptive text in facts | **Type 1 vs Type 2** per attribute. That's a conversation with the business |
| Converting a long SQL script into staged models | Materializes everything as `table`, or everything as `view` | **Materialization vs cost/freshness**. You know the data volumes and the SLA; AI doesn't |
| | Invents business rules (rounding, per-second vs per-minute billing) | **Business definitions**: what counts as "revenue", "active customer" |
