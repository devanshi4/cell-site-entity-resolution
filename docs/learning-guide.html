1. The business problem

Business problem

A telecom company has one physical thing (a cell site: a tower or rooftop with radios on it) and three departments that each keep their own records about it.

DepartmentSystemWhat they care aboutTheir ID for the site
Network engineeringNetwork Inventory (CSV export)What equipment is installed, where, and is it activeNY-BRONX-017
Radio planningRF Planning (JSON export)Exact coordinates, antennas, radio technology (LTE / 5G)RF-10017
Field operationsWork-order system (Parquet export)Technician visits: repairs, swaps, maintenanceWO-55001, WO-55002, … (one per visit)

Each system was built by a different team, at a different time, for a different purpose. Nobody agreed on a shared ID. So there is no column you can join on.

Questions the business asks that none of the three systems can answer alone:

  • "Which sites had an equipment swap in the field, but Inventory still shows the old vendor?" (needs Inventory + Field Ops)
  • "Which 5G sites had more than 2 corrective work orders this year?" (needs RF + Field Ops)
  • "Which RF-planned sites are missing from Inventory?" (needs RF + Inventory, and the ability to say "no match")
WHY To answer these, we must first decide which records describe the same physical site. That decision is called entity resolution (also called record linkage). An entity is the real-world thing (the physical site). A record is one row in one system that describes it. One entity can have many records. Entity resolution groups records by entity and gives each group one new ID we control: the canonical ID.

2. Architecture: who does what

Architecture

Before any technology names, here is the job that must be done, broken into four separate responsibilities. Interviewers often probe whether you know which system is responsible for what.

ResponsibilityQuestion it answersOn AWSLocally (on your laptop)
StorageWhere do the bytes physically live?Amazon S3 (object storage: files addressed by a key like s3://bucket/path/file.parquet)A folder on disk: warehouse/
ComputeWho reads the files, runs the SQL, and writes the results?Apache Spark running on EMR Serverless (AWS starts Spark machines for the job and removes them after)Spark in one process on your laptop (local[2])
Table formatWhich files together make up "the table" right now? What is its schema? What did it look like yesterday?Apache Iceberg: a set of metadata files stored in S3 next to the data, plus a Java library that runs inside SparkSame: Iceberg library inside local Spark, metadata files in warehouse/
CatalogWhen someone says silver.cell_site, which metadata file is the current one?AWS Glue Data Catalog: stores table name → location of the current Iceberg metadata fileAn Iceberg "Hadoop catalog": a small text file in the table folder pointing to the current version
A common misunderstanding to avoid in interviews: Iceberg is not a server or a database you log into. It is (1) a specification of how to lay out metadata files, and (2) a library that Spark, Athena, Trino, etc. load. There is no "Iceberg process" managing transactions. Transactions work because every writer follows the same rules, and the catalog performs one atomic step at the end: swap the pointer from the old metadata file to the new one. We will watch this happen with real files in Module 10.

How the systems connect

Read the numbered steps as "what happens when one Spark job updates one Iceberg table":

  1. Spark asks Glue: "Where is the current metadata file for silver.cell_site?" Glue answers with an S3 path.
  2. Spark reads from S3: that metadata file, then the manifests it points to, then only the data files it needs.
  3. Spark writes new files to S3: new data files, new manifests, and a brand-new metadata file. It never edits existing files. At this point readers still see the old version, because Glue still points to the old metadata file.
  4. Spark asks Glue to swap the pointer from the old metadata file to the new one, only if nobody else changed it in the meantime. This single swap is the commit. If the job crashed before step 4, the new files are just unreferenced garbage and the table is unchanged.

You don't need to understand all of this yet. Module 10 shows each of these files on disk. For now, remember the four responsibilities.

3. The three sources

Actual data

The data is small on purpose: 24 + 24 + 30 = 78 records describing 24 physical sites in New York City. Every record was written by hand to contain a specific, realistic problem. The file data/ground_truth/ground_truth.csv is the answer key: for each record, which physical site it really is, and what lesson it contains. In a real company you don't have this file; you create a small one by having people label pairs by hand (Module 7 explains why that matters).

WHY THIS TABLE MATTERS Look at which evidence each pair of sources shares:
  • Inventory ↔ RF: name, coordinates, borough. Strong.
  • Inventory ↔ Field Ops: name, street address, ZIP. Strong.
  • RF ↔ Field Ops: only the name (RF has no address, Field Ops has no coordinates). Weak.
So the evidence we can use depends on the pair of sources. That is why entity resolution is not one rule; it is a set of comparisons whose evidence differs. Keep this in mind for the second TRY-IT question below.

TRY IT 1 These are 9 records. How many physical sites are they, which records belong together, and what evidence did you use for each decision? Is there any record you cannot place?
Show answer (after you've tried)

2 physical sites, plus 1 record we cannot place with confidence.

  • S01, 1250 Grand Concourse: NY-BRONX-017, NY-BX-0017, RF-10017, WO-55001, WO-55002.
    • NY-BRONX-017 ↔ NY-BX-0017: same house number + street + base ZIP, coordinates 2.2 m apart. This is a duplicate inside one source with two different IDs. A legacy migration created a second ID.
    • NY-BRONX-017 ↔ RF-10017: coordinates 3.6 m apart, both in the Bronx, nearly identical names.
    • NY-BRONX-017 ↔ WO-55001 / WO-55002: house number 1250, same street (after you realize "CONCRS" is a misspelling of "Concourse" and "BX" is "Bronx"), same ZIP.
  • S02, 1100 Grand Concourse: NY-BRONX-018, RF-10018, WO-55003. These are 597 m from S01, on the same street, in the same ZIP. The name "Grand Concourse" appears in all of them. If you matched on name alone, you would merge two different sites. That error is called a false positive.
  • WO-55028 cannot be placed: "Grand Concourse, Bronx NY" has no house number and no ZIP. The equipment (Ericsson AIR 6449) hints S01, because S02 has Nokia, but equipment changes over time and many sites have the same model. A responsible pipeline does not guess. It sends this record to a manual review queue (Module 8).

Notice what you did in your head. You (1) mentally cleaned the text ("BX" → "Bronx"), (2) compared several attributes, (3) weighed them (a matching house number counts more than a matching street name, because many sites are on Grand Concourse), and (4) refused to decide when evidence was too weak. Those four steps are exactly Modules 2, 6, 7 and 8. We will turn your intuition into SQL.

TRY IT 2 RF-10017 has coordinates but no address. WO-55001 has an address but no coordinates. Their names are "Bronx Grand Concourse" and "Bx Grand Concourse Site". How could the pipeline confidently conclude they are the same site?
Show answer (after you've tried)

Directly, it mostly can't: the only shared evidence is the name, and names are weak (RF-10018 is also "Grand Concourse …").

But indirectly it can. RF-10017 matches NY-BRONX-017 strongly (coordinates 3.6 m apart). WO-55001 matches NY-BRONX-017 strongly (same address and ZIP). If A = B and B = C, then A = C. The inventory record acts as a bridge, because it is the only source with both coordinates and an address.

This is why entity resolution produces pairwise matches first and then groups them into clusters (the technical term is "connected components" of a graph where records are points and matches are lines). Module 8 builds this. It also shows the danger: one wrong pairwise match can chain two separate clusters together.

Interview question for this module

INTERVIEW "You have three systems describing the same entities with no shared key. Where do you start?"
A natural answer

"Before writing any matching logic I profile the sources, because the right rules depend on the evidence each source has. First I check the grain of each source: in our telecom data, inventory had one row per site, but field operations had one row per work order, so many rows mapped to one site. Then I list which attributes each pair of sources shares. Inventory and RF shared coordinates; inventory and field ops shared addresses; RF and field ops only shared a free-text name. That told us inventory would act as the bridge, and that RF-to-field-ops links would mostly come through it. I also look for duplicates inside each source and for data-quality problems such as swapped coordinates, because those break matching later."

Interview questions (grows every module)

What is entity resolution, in one sentence an interviewer will like?

"Deciding which records, across or within systems, describe the same real-world thing when there's no reliable shared key, and giving each real-world thing one stable ID with a traceable mapping back to every source record."

Which AWS component stores data, which processes it, which keeps table metadata, and which manages transactions?

S3 stores the bytes, both data files and Iceberg metadata files. Spark on EMR processes the data. Iceberg defines the table metadata (schema, snapshots, the list of data files), written as files in S3 by the Iceberg library running inside Spark. The Glue Data Catalog maps a table name to its current metadata file. There is no central transaction manager: each writer writes new files and then asks the catalog to atomically swap the pointer, which succeeds only if no one else committed first. That is optimistic concurrency.

Why does Field Operations have more rows than there are sites?

Because its grain is a work order, not a site. One site gets many visits. If you joined inventory to field ops and counted rows, you'd over-count sites. Always state the grain of a table before joining it.
