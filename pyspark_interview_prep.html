Interview playbook

What to expect, how to talk while coding, and how to ask clarifying questions.

What the interview looks like

  • Format: 60-minute Zoom with two engineers. They share a link to a coding environment, you code while talking through it.
  • The link is usually one of: CoderPad (app.coderpad.io/…), a Databricks notebook, Google Colab (colab.research.google.com/drive/…), or HackerRank / CodeSignal. It opens in your browser.
  • Screen sharing: on CoderPad they see your code live. On Colab or Databricks they'll likely ask you to share your screen, so check Zoom screen-sharing permission beforehand (Mac: System Settings → Privacy → Screen Recording). Close extra tabs and turn off notifications.
  • It's fine to ask the recruiter which platform the link will be for.

How to talk without losing concentration

Interviewers don't expect nonstop narration. They dislike unexplained silence, not silence. Talk at the moments you're not typing.

PhaseWhat you doTalking?
1. PlanSay your approach in 2–3 sentences before typing.✅ Most important
2. TypeWrite the code. Say "Let me write this, give me a minute."🤫 Quiet is fine
3. ExplainRun it, read the output, say whether it's what you expected.✅ Yes

Best trick: write the plan as comments first, and read them aloud as you type them. You decide a step, then say it. Then fill in the code under each comment quietly.

# 1. filter out invalid rows
# 2. aggregate calls per tower
# 3. join with towers to get region
# 4. sum per region
"I concentrate better if I write a block first and then walk you through it. Is that okay?"
When stuck: "I know I need the previous row here. I'm trying to remember if it's lag or lead."
When you don't know: "I haven't used that directly, but here's how I'd reason about it… and I'd confirm by checking the Spark UI / docs / testing on a sample."

Predict before you run. Saying "I expect one partition to be much bigger" before running is strong. If it matches, you look like you understand the system. If not, you have something interesting to discuss.

How to ask clarifying questions

Formula: What I noticed → the question → what I'd do by default

The default is what sets you apart: it shows you have an opinion and won't stall waiting for an answer.

Weak
"I see that values are null, so should they count?"
Strong
"About 10% of calls have a null tower_id, so they can't be matched to a region. Should they appear? My default would be an 'Unknown' region, so the totals still add up and the team sees how much is missing."
Weak
"Are there duplicates so I can drop them first?"
Strong
"Is call_id unique? If yes I'll skip dedup, since it's a shuffle. If not, I'll dedup on call_id before aggregating."

GroupQuestions

How to answer discussion questions

1. What's the problem → 2. How I'd confirm it → 3. What I'd change → 4. The trade-off

Steps 2 and 4 signal real experience: "I'd check the Spark UI first", "the downside is…".

Part 1: Total revenue per customer

Calculate the total revenue per customer, counting only completed orders. Show the customer's name with their total, highest first. Customers with no completed orders should still appear with 0.

Clarifying questions

"Orders 105 and 106 are identical except for the ID. Did the POS resend it, or are they two orders?"Upstream does send duplicates. For Part 1, treat them as separate. Dedup is Part 2.

Model answer

"I'll aggregate orders to one row per customer first, so both sides are at the same grain when I join. That avoids fan-out and shuffles less data. Then a left join from customers so nobody is lost, and fill missing totals with 0."

    .fillna({"total_rev": 0})
    .select("customer_id", "name", "total_rev")          # follow the spec exactly
    .orderBy(F.desc("total_rev"), "customer_id"))        # tiebreaker = deterministic

Handling Dave vs Eve in code

Option 1 (recommended): keep the information that tells them apart.

completed = orders.filter(F.col("status") == "completed")

total = completed.groupBy("customer_id").agg(
    F.sum("amount").alias("total_rev"),
    F.count("*").alias("completed_orders"),                       # counts every row
    F.sum(F.when(F.col("amount").isNull(), 1).otherwise(0))
        .alias("orders_missing_amount"))

final = (customers.join(total, "customer_id", "left")
    .fillna({"total_rev": 0, "completed_orders": 0, "orders_missing_amount": 0})
    .select("customer_id", "name", "total_rev", "completed_orders", "orders_missing_amount")
    .orderBy(F.desc("total_rev"), "customer_id"))

Option 2: a status label

final = final.withColumn("revenue_status",
    F.when(F.col("completed_orders") == 0, "no_orders")
     .when(F.col("orders_missing_amount") > 0, "incomplete")
     .otherwise("complete"))

Option 3: quarantine bad rows (production pattern)

bad_rows  = orders.filter(F.col("amount").isNull())     # -> quarantine table + alert source team
good_rows = orders.filter(F.col("amount").isNotNull())  # -> continue the pipeline
"I'd keep Dave's and Eve's cases separate. In the report I'd add a completed-orders count and a missing-amount flag, so a 0 is never ambiguous. In production I'd send null-amount rows to a quarantine table and alert the source team, instead of silently fixing them."

Tip: F.count("*") counts all rows; F.count("amount") skips nulls. Comparing them finds missing values. F.coalesce(col, F.lit(0)) is an alternative to fillna.

Part 2: Deduplication

Two orders are duplicates when they have the same customer_id, order_date, amount and status. Keep the one with the lowest order_id.
  1. Build orders_clean.
  2. Show how many rows were removed (for data-quality monitoring).
  3. Rerun the Part 1 report on clean data.
Discussion: a built-in function could do this in one line. Why might you not use it?
"Same four columns means the POS resent it, and the rule says keep the lowest order_id. So I'll partition a window by those four columns, order by order_id, and keep row number 1. I'll keep the other rows too, so I can log exactly what was removed."
w = Window.partitionBy("customer_id", "order_date", "amount", "status").orderBy("order_id")

ranked = orders.withColumn("rn", F.row_number().over(w))

orders_clean = ranked.filter("rn = 1").drop("rn")
removed      = ranked.filter("rn > 1").drop("rn")   # exactly order 106

removed.show()
print("rows removed:", removed.count())

Showing the removed rows beats subtracting two counts: you get the actual records (useful for an audit/quarantine table), and orders.count() + orders_clean.count() runs two full jobs.

Step 3: rerun the report. With clean data, Carol drops from 120 to 60. Don't skip sub-parts: if you need to, say "I'll come back to step 3."

Why not dropDuplicates?

orders.dropDuplicates(["customer_id", "order_date", "amount", "status"])
  • It doesn't let you choose which row survives. After a shuffle, which row is kept is effectively random, so "keep the lowest order_id" isn't guaranteed.
  • Two runs could keep different rows: the pipeline becomes non-deterministic.
  • It's fine when rows are completely identical in every column.
"dropDuplicates keeps an arbitrary row, and we have a business rule about which one to keep, so I used row_number with an explicit order. It's deterministic, and I can capture the removed rows for auditing."
  • row_number vs rank vs dense_rank: for dedup always use row_number. If two rows tied on the order column, rank gives both 1 and keeps both.
  • Nulls in partition keys are grouped together, so two rows with null amount and matching other keys count as duplicates.

Part 4: Discussion questions (no code)

Q1 · "orders is now 2 billion rows. What changes?"

"The logic stays the same, but I'd change how data is stored, read and moved.

Storage: Parquet or Delta, not CSV, partitioned by order_date, so date filters only read those folders (partition pruning). Parquet also reads only selected columns (column pruning) and pushes filters into the scan (predicate pushdown).

Reduce early: filter and select first; aggregate before joining so the join gets one row per customer.

Watch shuffles: my dedup key includes order_date, so duplicates only occur within a day, and I can dedup one day's partition at a time. And I'd never run the no-partitionBy monthly window on raw rows.

Fewer actions: remove count()/show(); cache only what's reused.

Config: Adaptive Query Execution on (default since Spark 3.2) and a sensible spark.sql.shuffle.partitions; the default 200 is often wrong."

Key idea: read less, shuffle less, act less.

Q2 · "The join with customers is slow. Why, and what would you try?"

"I'd check .explain() or the Spark UI for the join strategy. Two large DataFrames get a sort-merge join: both sides shuffled by key and sorted, which is the slow part. But customers is a small dimension table, so I'd broadcast it: every executor gets a full copy and the big table doesn't shuffle at all. Spark auto-broadcasts under spark.sql.autoBroadcastJoinThreshold (10 MB by default) and AQE can switch at runtime; the hint makes it explicit. Trade-off: the broadcast table must fit in memory on the driver and every executor. If both sides are large: filter and prune first, check for skew, and consider bucketing tables joined repeatedly."
result = orders.join(F.broadcast(customers), "customer_id", "left")

Gotcha: in a left join Spark can only broadcast the right side.

Q3 · "What is data skew? How do you spot and fix it?"

Covered in depth in Mock 2. Short version: a few keys have far more rows; during a shuffle all of a key's rows go to one task, so one task does most of the work and the stage waits on it. Spot it in the Spark UI (median task seconds, max task minutes) and confirm with groupBy(key).count(). Fix in order: handle bad keys (nulls, placeholders) separately → broadcast → AQE skew join → salting.

# Salting for a skewed SUM (random salt is fine for sums)
salted  = orders.withColumn("salt", (F.rand() * 10).cast("int"))
partial = salted.groupBy("customer_id", "salt").agg(F.sum("amount").alias("part_sum"))
final   = partial.groupBy("customer_id").agg(F.sum("part_sum").alias("total"))

Q4 · "How would you make this pipeline incremental?"

"Each run should process only new or changed data. Three things: what's new, where it goes, and making reruns safe.

1. New data: a high-water mark in a control table, using an ingestion timestamp, not order_date, because orders arrive late.

2. Writing: MERGE (upsert) with Delta or Iceberg on order_id; for aggregates, recompute only affected partitions with dynamic partition overwrite.

3. Dedup across batches: a resend can arrive in a different batch, so the merge must check incoming rows against the existing table on the business key.

4. Idempotency: MERGE and partition overwrite give the same result if rerun; a plain append doesn't, which is a classic source of duplicates.

5. Late data: reprocess a lookback window, e.g. the last 3 days, each run."

If pushed: Structured Streaming with a watermark and dropDuplicatesWithinWatermark for near-real-time. On AWS: S3 (Parquet/Delta/Iceberg), Glue or EMR, Airflow or Step Functions, and Glue job bookmarks as a built-in high-water mark.

Quick-fire questions

QuestionShort answer
Transformation vs action?Transformations (filter, select, join) are lazy and build a plan. Actions (count, show, write, collect) run it.
Why is Spark lazy?Seeing the whole plan lets the Catalyst optimizer reorder and combine steps, e.g. push filters down.
Narrow vs wide?Narrow (filter, withColumn): no data movement. Wide (groupBy, join, distinct, window with partitionBy): needs a shuffle.
repartition vs coalesce?repartition(n): full shuffle, can go up or down, even. coalesce(n): only down, no full shuffle, can be uneven. Use coalesce to reduce output files.
When to cache?When a DataFrame is reused by several actions. Not for one-time use. unpersist() after.
Small files problem?Many tiny files slow reads (metadata, task overhead). Coalesce/repartition before writing, or compact (Delta OPTIMIZE).
Why avoid collect()?Pulls everything to the driver → out of memory on big data.
Why avoid Python UDFs?Opaque to the optimizer, plus JVM↔Python serialization. Use built-ins, or pandas UDFs.
groupBy vs window?groupBy collapses rows to one per group. A window keeps every row and adds a column.

Part 1: The region report

For each region: total number of calls, total call minutes (duration_sec is seconds), average duration in minutes (2 decimals). Sort by total minutes, highest first.

Common mistakes (seen in the first attempt)

1. Wrong grain. Stopping at one row per tower. The spec says per region, so a second groupBy("region") is needed after the join.

2. Rounding too early. Rounding each call to minutes then summing accumulates rounding errors over billions of rows.

3. Averaging averages. Averaging tower averages weights a 1.2M-call tower the same as a 600-call tower. Wrong.

Rule: carry sums and counts through the pipeline; divide and round only at the very end.

Model answer

# 1. aggregate per tower, keeping raw seconds
# 2. broadcast-join towers to get region (towers is tiny)
# 3. null region -> 'Unknown'
# 4. roll up to region, convert and round at the end

tower_agg = cdr.groupBy("tower_id").agg(
    F.count("*").alias("n_calls"),
    F.sum("duration_sec").alias("total_sec"))

with_region = (tower_agg
    .join(F.broadcast(towers), "tower_id", "left")
    .fillna({"region": "Unknown"}))

report = (with_region.groupBy("region").agg(
        F.sum("n_calls").alias("total_calls"),
        F.sum("total_sec").alias("total_sec"))
    .withColumn("total_minutes", F.round(F.col("total_sec") / 60, 2))
    .withColumn("avg_minutes",   F.round(F.col("total_sec") / 60 / F.col("total_calls"), 2))
    .drop("total_sec")
    .orderBy(F.desc("total_minutes")))

Expect Downtown first (~1.2M calls), Unknown second (~200k), then ten Region_x rows with ~60k calls each, average ~5 minutes everywhere.

⭐ Why this design already avoids most of the skew

The join happens after aggregation: ~1,000 rows on each side, nothing to skew. And the groupBy("tower_id") uses count/sum, which Spark pre-aggregates on each partition before the shuffle (map-side combine). Tower 1's 1.2M rows become one partial row per partition before anything moves.

"The slow production job probably joins raw CDRs to towers first. In a sort-merge join, all 1.2 million tower-1 rows, plus the 200,000 nulls, get shuffled to single tasks. That's the skew. My version aggregates first; Spark pre-aggregates each partition, so the hot key shrinks to a handful of rows and the join is only ~1,000 × 1,000. Broadcasting towers removes the join shuffle entirely."

Nulls: they form one group in a groupBy and hash to one partition in a shuffle. Null keys never match in a join, which is why they come out with a null region.

⭐ Hash salt, not random salt

 RANDOM salt  (wrong for distinct)       HASH salt  (correct)
 caller 42 → bucket 1, 3, 6              caller 42 → always bucket 5
 counted 3 times ❌                       counted once ✅
"Random salt is fine for sums, since any split of numbers adds back up. For distinct counts it double-counts: one caller's calls land in several buckets. With hash(caller_id) % N a caller always lands in the same bucket, so the buckets hold disjoint sets of callers and summing their distinct counts is exact. Downtown is now spread over 8 tasks."

Bonus points

Approximate is OK?

approx = base.groupBy("region").agg(
    F.approx_count_distinct("caller_id", rsd=0.01).alias("approx_unique_callers"))
"approx_count_distinct uses HyperLogLog sketches, which can be merged, so Spark pre-aggregates them like a sum: no skew, little memory, ~1% error. Fine for a planning dashboard, not for billing."

Simplest alternative: base.distinct().groupBy("region").count(). distinct() shuffles by (region, caller_id), spreading Downtown out. Effectively the same idea as the hash salt.

Spark already helps: naive.explain() shows Spark rewrites a single countDistinct into two aggregation steps (first by region + caller_id). Doing it by hand matters with several distinct counts, or for operations Spark can't split (collect_set, percentiles, windows partitioned by a hot key).

Don't add regions up: the same caller appears in many regions, so company-wide unique callers needs its own countDistinct.

Salting deep dive

Random vs hash salt, salting a join when both tables are big, and how to choose N.

Key idea: salting deliberately splits one hot key across several buckets. That's what fixes the skew. A second groupBy on the key alone (or a join on key + salt) puts the pieces back together. The real question is: what has to stay together for the answer to be correct? That decides which salt to use.

Side by side: random salt vs hash salt

Tower 1 has 6 calls, split into 2 buckets. Correct answers: 6 calls, 3 unique callers (A, B, C).

call_id  caller
c1       A
c2       A
c3       B
c4       C
c5       A
c6       B

Random salt
(F.rand() * 2).cast("int")

Each row is assigned by chance:

Bucket 0: c1 A, c3 B, c6 B
Bucket 1: c2 A, c4 C, c5 A
bucketcallsunique callers
032 (A, B)
132 (A, C)
sum6 ✅4 ❌

Caller A is in both buckets, so A is counted twice.

✅ Perfectly even split (3 and 3)

Hash salt
F.pmod(F.hash("caller_id"), F.lit(2))

Each caller always lands in the same bucket (A→1, B→0, C→1):

Bucket 0: c3 B, c6 B
Bucket 1: c1 A, c2 A, c4 C, c5 A
bucketcallsunique callers
021 (B)
142 (A, C)
sum6 ✅3 ✅

Each caller is in exactly one bucket, so the counts add up correctly.

⚠️ Less even (2 and 4)

Hash salting is only as even as the column you hash. If caller A were a robocaller with 1 million calls, bucket 1 would still be huge. Random salt is the most even split possible, and that's why it exists: use it when nothing needs to stay together. A sum, count, min or max gives the same answer however you split the rows.

OperationWhat must stay together?Salt to use
sum, count, min, maxNothingRandom (most even)
countDistinct("caller_id")All rows of the same callerhash(caller_id)
Join (both tables large)Each row must still meet its matching rows on the other sideRandom or hash on one side, copies on the other (below)
Running total per keyAll rows of the key, in orderSalting doesn't work simply. Rethink the logic.
Caution about F.rand(): if Spark retries a failed task, it recomputes rand(), and rows can get different salts the second time. For a sum that's harmless. In a join it can cause missing or duplicated rows. A safer choice is F.pmod(F.hash("call_id"), F.lit(N)): because call_id is unique, it spreads rows almost as evenly as random, but every rerun gives the same salt. Think of it as "random, but repeatable".

When both tables are big and you can't broadcast

Scenario: join cdr (2 billion rows, tower 1 = 60%) with tower_signal_logs (also billions of rows, signal readings every few seconds per tower). Neither fits in memory, so Spark uses a sort-merge join, and all of tower 1 from both sides goes to one task.

Step 0: let Spark try first.

"First I'd make sure AQE skew join is enabled. It's on by default in Spark 3. It detects partitions much larger than the median (by default more than 5× the median and over 256 MB), splits them into smaller pieces, and copies the matching partition from the other side. That's automatic salting. I'd salt by hand only if AQE doesn't handle it, for example with an unsupported join type, or if it's still too slow."

Why random salt on both sides fails: tower-1 rows in cdr with salt 3 need tower-1 rows in logs with salt 3. But each logs row got only one random salt, so most matches are lost.

The fix: salt the big skewed side, copy the other side.

cdr  (salt each row 0..N-1)        logs (copy each tower-1 row N times)
tower 1, salt 0  ─────────────────► tower 1, salt 0
tower 1, salt 1  ─────────────────► tower 1, salt 1
tower 1, salt 2  ─────────────────► tower 1, salt 2
...                                 ...
join ON (tower_id, salt)

Each cdr row has exactly one salt and logs has a copy for every salt, so each cdr row finds its match exactly once: no lost rows, no duplicates, and tower 1's work is spread over N tasks.

Only salt the hot keys. Copying the other side N times is expensive, so leave everything else as a normal join:

N = 8
hot = [1]   # found with groupBy("tower_id").count()

# Big skewed side: hot keys get a salt 0..N-1, everything else gets 0
cdr_s = cdr.withColumn("salt",
    F.when(F.col("tower_id").isin(hot), F.pmod(F.hash("call_id"), F.lit(N)))
     .otherwise(F.lit(0)))

# Other side: hot keys copied N times (one per salt), everything else once with salt 0
logs_s = (logs
    .withColumn("salts",
        F.when(F.col("tower_id").isin(hot), F.sequence(F.lit(0), F.lit(N - 1)))
         .otherwise(F.array(F.lit(0))))
    .withColumn("salt", F.explode("salts"))
    .drop("salts"))

joined = cdr_s.join(logs_s, ["tower_id", "salt"]).drop("salt")

Only tower 1's rows in logs are copied N times; the other 999 towers are unaffected. Alternative: split the job into two joins (hot keys one way, everything else normally) and union the results. Same idea, written differently.

Edge case: if tower 1 is huge on both sides, the join output for tower 1 is huge too (every call × every log row). Salting spreads the work but can't shrink the output. Then question the join itself, e.g. aggregate the logs per minute first.

How to choose N

N = 8 in the mock was mostly arbitrary: it matched the 8 shuffle partitions in Colab. The proper way:

Goal: each bucket of the hot key should be about the size of a normal task.
N ≈ rows (or bytes) of the hot key ÷ rows (or bytes) in a typical partition
Colab mockProduction
Hot key (tower 1)~1.2 million rows60% of 2 billion = ~1.2 billion rows
Typical / target task~75,000 rows~128–256 MB of shuffle data, say ~5 million rows
N1.2M ÷ 75k ≈ 161.2B ÷ 5M ≈ 240

With N = 8 in Colab each bucket is ~150,000 rows, twice a normal task: much better than 16×, but 16 would have been the better choice.

N too smallN too large
The hot key's buckets are still bigger than normal tasks, so it stays partly skewed. Aggregation: N partial rows per key, a small extra cost.
Join: the other side is copied N times. This is the real cost, so in joins use the smallest N that fixes the problem.
Tiny tasks: scheduling overhead outweighs the work.
  • Different hot keys can get different N. Tower 1 with 1.2 billion rows → N = 240; tower 7 with 50 million → N = 10.
  • Measure, then adjust. Start with the estimate, run it, check the Spark UI. Max task time still far above the median → increase N. Copied side blowing up → decrease it.
  • Get the numbers cheaply: groupBy("tower_id").count() for the hot key's size; Spark UI shuffle-read sizes for typical task size.
"I'd choose N so each piece of the hot key is roughly the size of a normal task: the hot key's size divided by a typical partition's size. With 1.2 billion rows on the hot key and around 5 million rows per healthy task, that's about 240. In a join I'd keep N as small as works, because the other side is copied N times. I'd salt only the hot keys, and check the Spark UI afterwards to tune it."

Salting in four lines

  1. Salting deliberately splits a hot key. The second groupBy (or the join on key + salt) puts it back together correctly.
  2. What must stay together decides the salt: nothing → random (most even); a distinct column → hash of that column; a join → random/hash on one side and copies on the other.
  3. Both-big joins: AQE skew join first → salt only the hot keys → watch the cost of copying.
  4. N ≈ hot-key size ÷ normal task size. Bigger isn't free, especially in joins.

Skew summary

SituationSkew?Fix
count / sum / avg by a hot keyMostly no: pre-aggregated before the shuffleAggregate before joining
Join raw data to a small table on a hot keyYesBroadcast the small table
Join two large tables on a hot keyYesAQE skew join → isolate hot key → salt + replicate
countDistinct by a hot keySome riskHash salt on the distinct column, distinct() first, or approx_count_distinct
collect_list, percentile, window partitionBy(hot_key)Yes: can't be pre-aggregatedIsolate the hot key, or rethink the logic
Null keysYes: all nulls hash to one partitionFilter out, process separately, union back
The rule behind all of it: can this operation be split into pieces and combined afterwards? If yes, Spark mostly handles the skew. If no, split the work yourself, and make sure the split keeps the answer correct.

Skew in 30 seconds

What: a few keys have far more rows; in a shuffle each key goes to one task; one task does most of the work.

Spot: Spark UI median vs max task time · groupBy(key).count() · rows per partition after shuffle.

Fix, in order: 1. handle nulls/placeholder keys separately · 2. aggregate before joining · 3. broadcast the small side · 4. AQE skew join (spark.sql.adaptive.skewJoin.enabled) · 5. salting (hash salt for distinct) · 6. approximate functions if acceptable.

Trade-offs: broadcast must fit in memory · salting adds a second aggregation and complexity · approximate ≈1% error.

Performance in one line

Read less, shuffle less, act less. Parquet/Delta + partition by date (pruning, pushdown) · filter and select early · aggregate before joins · broadcast small tables · avoid extra actions, cache only what's reused · AQE on, tune shuffle partitions.
